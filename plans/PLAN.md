# Детальный план: Kotlin-блокчейн, TDD, материалы для отчёта и адаптивный TUI

## 1. Архитектура, зависимости и стиль

Приложение реализуется в одном Gradle-модуле. Сначала создаются модели и контракты, проверяются их инварианты, затем
через TDD реализуются компоненты блокчейна, сохранение результатов и консольные сценарии. Полноценный TUI
разрабатывается последним — после успешных тестов логики.

Целевая платформа — Windows x64. Итоговый дистрибутив — один `ConsoleBlockchain.exe`, не требующий Java, Gradle и
исходников. Допускается извлечение встроенной DLL Mosaic во временный каталог.

### Kotlin Coding Conventions

Следовать [официальным конвенциям Kotlin](https://kotlinlang.org/docs/coding-conventions.html):

- Четыре пробела, `UpperCamelCase` для типов, `lowerCamelCase` для функций и свойств.
- `val`, неизменяемые публичные коллекции, явное копирование данных на границах состояния.
- Связанные объявления и extensions размещать рядом; файлы называть по назначению: `HexEncoding`, `TransactionEncoding`,
  без общего `Utils`.
- Использовать `data class` для данных, `value class` для различаемых значений, sealed-типы для результатов.
- Не добавлять интерфейс каждому классу, DI-фреймворк, рефлексию для сериализации и универсальные репозитории.
- Ошибки пользователя возвращать как типизированный результат; исключения не использовать как штатный результат проверки
  блока.
- Добавить `.editorconfig`, сохранить `kotlin.code.style=official`.

## 2. Модели и контракты

Пакеты внутри `com.egorroman.blockchain`: `model`, `crypto`, `ledger`, `consensus`, `report`, `app`, `tui`.

### Простые модели

| Группа       | Типы и назначение                                                                                          |
|--------------|------------------------------------------------------------------------------------------------------------|
| Значения     | `Address`, `Hash256`, `PublicKeyHex`, `SignatureHex` — строковые `value class` с проверкой формата и длины |
| Кошельки     | `WalletInfo` — имя, публичный ключ, адрес; без закрытого ключа                                             |
| Транзакции   | `TransactionBody`, `SignedTransaction`                                                                     |
| Цепочка      | `BlockHeader`, `Block`, `Genesis`, `Allocation`                                                            |
| Состояние    | `AccountState`, `LedgerSnapshot`, `BlockchainSnapshot`                                                     |
| Меркл        | `MerkleTree`, `MerkleLevel` с отметкой дублированного узла                                                 |
| Проверки     | `ValidationError`, `ValidationResult`, `BlockValidation`                                                   |
| Согласование | `NodeId`, `Vote`, `CandidateEvaluation`, `ConsensusResult`                                                 |
| Эксперименты | `ExperimentResult`, `SessionReport`, события лабораторной работы                                           |

Суммы, nonce и индексы — `Long`. Проверять допустимость значений и переполнение. В постоянных моделях хранить
HEX-строки; `ByteArray` использовать на границах криптографии, избегая проблем сравнения массивов в `data class`.

Структура Kotlin-моделей может содержать вложенный `TransactionBody`, но каноническая транзакция должна оставаться
плоским объектом с точными полями из методички.

Закрытые ключи хранить в приватном состоянии компонента подписи. Они не входят в сериализуемые модели, снимки,
результаты операций или `toString()` публичных объектов.

### Основные интерфейсы

| Интерфейс              | Контракт                                                                                          |
|------------------------|---------------------------------------------------------------------------------------------------|
| `WalletSigner`         | `createWallet(name): WalletInfo`, `sign(address, message): SignatureHex`                          |
| `Cryptography`         | `sha256(message): Hash256`, `verify(publicKey, message, signature): Boolean`                      |
| `CanonicalEncoder`     | `encode(value: JsonElement): ByteArray`                                                           |
| `TransactionValidator` | `validate(transaction, snapshot): ValidationResult`                                               |
| `BlockValidator`       | `validate(block, snapshot): BlockValidation`                                                      |
| `ConsensusEngine`      | `run(candidates, snapshot, abstainingNodes): ConsensusResult`                                     |
| `ReportStore`          | Сохранение публичного события и обновление сводных материалов с типизированным результатом записи |

`BlockValidation.Valid` содержит рассчитанное состояние после блока. Проверяющие компоненты не изменяют исходный снимок.

Класс `Blockchain` владеет состоянием сессии: создаёт снимки, принимает переводы в pending, формирует кандидатов и
фиксирует победителя. Проверка и фиксация остаются разными операциями.

Интерфейсы сначала получают документацию контрактов. Их поведение проверяется на реальных реализациях; тесты
существования интерфейса или поведения mock-объектов не писать.

## 3. Последовательность разработки через TDD

Каждое новое поведение проходит цикл: **тест → ожидаемое падение → минимальная реализация → успешный тест → рефакторинг
**. После завершения этапа запускать весь набор тестов. Компиляционный каркас допустим, но законченные методы с `TODO()`
не оставлять.

### Этап 1. Сборка и зависимости

- Настроить версии, плагины, репозитории, Java 21 и JUnit Platform.
- Подключить перечисленные зависимости; наличие Mosaic в сборке не означает начало разработки TUI.
- Проверить `dependencies` и `dependencyInsight` для Kotlin, Compose и JUnit.
- Убедиться, что тестовые и прикладные classpath разрешаются без конфликтов.

### Этап 2. Модели, контракты и чистые функции

- Создать объявления моделей и интерфейсов.
- До реализации проверок написать тесты форматов HEX, длин адресов/ключей/подписей, диапазонов чисел и защиты снимков от
  изменения исходных коллекций.
- Реализовать необходимые инварианты, HEX-преобразования и небольшие extensions.
- Не тестировать автоматически сгенерированные getters, `copy()` и `equals()` без собственного поведения.

Результат: простой типизированный фундамент с успешными тестами, без реализации блокчейн-сервисов.

### Этап 3. Каноническая сериализация и криптография

Тестами зафиксировать:

- Точный компактный JSON и сортировку ключей, включая вложенные объекты.
- Сохранение порядка массивов, UTF-8 и ограничения подписываемых значений.
- Исключение `tx_id` и `signature` из подписываемого тела.
- Известные SHA-256-векторы и Ed25519-вектор из RFC 8032.
- Преобразование публичного ключа в 32 raw-байта и обратно.
- Успех для исходного сообщения, отказ для изменённого сообщения и другого ключа.

Затем реализовать `CanonicalEncoder`, `Cryptography`, `WalletSigner` и функции формирования канонических объектов.

### Этап 4. Кошельки и genesis

- Проверить независимость трёх кошельков и вычисление адресов.
- Зафиксировать точные правила genesis: нулевые поля, пустые транзакции, отсортированные allocations.
- Проверить получение балансов и nonce из genesis.
- Проверить обнаружение изменения allocations и отсутствие секретов в публичном представлении.

Затем реализовать создание и проверку начального состояния.

### Этап 5. Транзакции и pending

- Проверить сумму, адреса, ключ, подпись, tx_id, nonce и подтверждённый баланс.
- На границе ввода отклонять дробные, логические и выходящие за диапазон значения.
- Проверить отдельные результаты N0/N1/N2, требование трёх успешных проверок и добавление одного экземпляра.
- Проверить неизменность балансов, запрет второй pending-записи отправителя и отклонение повторной подтверждённой
  операции.

Затем реализовать `TransactionValidator` и операции очереди.

### Этап 6. Меркл и блоки

- Для 1/2/3 записей использовать независимо подготовленные ожидаемые значения.
- Проверить байтовое соединение хэшей, дублирование третьего узла и изменение корня при перестановке.
- Проверить размер блока, повтор tx_id, индекс, предыдущий хэш, корень и заголовок.
- Проверить последовательное применение переводов на временном состоянии.
- Проверить отсутствие частичного применения при ошибке последней транзакции.
- Проверить фиксацию только актуального кандидата и удаление только включённых pending-записей.

Затем реализовать построение дерева, `BlockValidator` и атомарную фиксацию.

### Этап 7. Согласование и проверка цепочки

- Подготовить B1/B2/B3 согласно методичке.
- Проверить корректность B1/B2 и отказ B3 именно по подписи после пересчёта остальных хэшей.
- Проверить минимальный хэш, независимость от порядка кандидатов и отсутствие повторного подсчёта одинаковых предложений
  и голосов.
- При двух `NO_VOTE` проверить неизменность chain, balances, nonce и pending.
- Проверить обнаружение повреждений genesis и копии принятой цепочки.

Затем реализовать `ConsensusEngine` и проверку цепочки.

### Этап 8. Материалы отчёта и неинтерактивные сценарии

- Реализовать сохранение по правилам следующего раздела.
- Проверить полноту обязательных материалов, отсутствие секретов и сохранение неуспешных операций.
- Реализовать `--demo`, `--experiments`, `--output-dir`.
- Проверить контрольные балансы **95/90/115**, nonce **1/1/1**, пустой pending и сумму **300**.
- Успешный сценарий возвращает код `0`, провал проверки — `1`, неправильные аргументы — `2`.

**Только после успешного завершения этапов 1–8 начинается работа над TUI.**

### Этап 9. Проверка нативной упаковки

До разработки всех экранов проверить небольшой технический стенд Mosaic: вывод, клавиатуру, resize и завершение в Native
Image.

- Использовать GraalVM для JDK 21 и Native Build Tools 1.1.14.
- Подготовить reachability/JNI/resource metadata для встроенной DLL и callbacks Mosaic.
- Инициализацию загрузчика DLL и генерацию ключей выполнять во время запуска приложения.
- Собирать с `--no-fallback`, исключая EXE, требующий установленной JVM.
- Проверить Ed25519, сериализацию и оба консольных сценария в нативном исполнении.

GraalVM и MSVC Build Tools с Windows SDK нужны только на машине сборки. Поддержка JNI предусмотрена GraalVM, но
совместимость всего набора библиотек подтверждается этим стендом, а не предполагается
заранее. [GraalVM для Windows](https://www.graalvm.org/latest/getting-started/windows/), [JNI в Native Image](https://www.graalvm.org/latest/reference-manual/native-image/dynamic-features/JNI/).

### Этап 10. TUI и окончательная сборка

Реализовать общие компоненты дизайн-системы, затем экраны. Сохранить работу готовых headless-сценариев и повторно
проверить итоговый EXE.

## 4. Сохранение материалов и адаптивный TUI

### Материалы для отчёта

Автоматически сохранять результат каждой завершённой предметной операции, включая отказы. Просмотр экрана или
перемещение курсора запись не создают.

Каждая ручная, демонстрационная и экспериментальная сессия получает отдельный каталог с уникальным идентификатором. По
умолчанию — в `%LOCALAPPDATA%\ConsoleBlockchain\sessions`; `--output-dir` задаёт другой корневой каталог.

| Файл              | Содержание                                                                        |
|-------------------|-----------------------------------------------------------------------------------|
| `metadata.json`   | Версия приложения, инструментов и библиотек, ОС, время и тип сессии               |
| `events.jsonl`    | Последовательность полных публичных результатов с номерами шагов                  |
| `journal.txt`     | Читаемый протокол действий, проверок и причин отказа                              |
| `summary.md`      | Материалы для переноса в отчёт: описание опыта, таблицы, дерево и выводы проверок |
| `candidates.csv`  | Сравнение B1/B2/B3 по шаблону методички                                           |
| `balances.csv`    | Балансы и nonce до и после операций                                               |
| `experiments.csv` | Ожидаемый и фактический результат каждого обязательного эксперимента              |

В события обязательно включать:

- Публичные ключи, raw-байты в HEX и производные адреса.
- Исходное и изменённое сообщения, подпись и результаты проверок.
- Полную подписанную транзакцию, каноническое тело и подписываемые байты в HEX.
- Результат каждого узла при рассылке.
- Все уровни Меркла для 1/2/3 записей.
- Полные заголовки, хэши и результаты проверки B1/B2/B3.
- Голоса, исключённые кандидаты, победителя или `NO_QUORUM`.
- Состояние до и после принятия либо отказа.
- Результаты проверки повреждённых копий цепочки.

События сохранять после каждого завершённого шага; сводные файлы обновлять из накопленных результатов. CSV писать в
UTF-8 BOM с корректным экранированием для Excel.

При ошибке записи показывать причину и сохранять результаты в памяти для повторного экспорта. Ошибка файловой системы не
отменяет уже принятую корректную операцию блокчейна. Закрытые ключи и seed никогда не записываются.

### Дизайн-система и адаптация

Сохранить выбранную тёмную тему:

| Роль                      | Цвет                              |
|---------------------------|-----------------------------------|
| Фон / поверхность         | `#0F172A` / `#1E293B`             |
| Текст / вторичный текст   | `#E2E8F0` / `#94A3B8`             |
| Рамки                     | `#475569`                         |
| Акцент                    | `#38BDF8`                         |
| Успех / ожидание / ошибка | `#4ADE80` / `#FBBF24` / `#FB7185` |

Общие токены: внешний отступ 1 колонка, внутренний горизонтальный отступ 2, промежуток между панелями 2, между группами
1 строка. Одинарные рамки, обычный текст и полужирные заголовки. Шрифт задаётся терминалом.

Общие компоненты: оболочка, панель, таблица, поле, действие, статус, подробности и подсказки клавиш. Цвета и размеры не
дублировать по экранам.

Адаптивная компоновка:

- **80–99 колонок:** одна рабочая область, меню разделов открывается через F2.
- **100–139 колонок:** боковое меню 22 колонки и растягиваемая рабочая область.
- **От 140 колонок:** список и подробности выбранной записи отображаются рядом там, где это полезно.
- Высота содержимого рассчитывается по доступному пространству; длинные таблицы и подробности прокручиваются.
- Минимальный размер — **80×24**. При уменьшении ниже минимума показывается сообщение с текущим размером; состояние
  формы и выделение сохраняются.
- Resize пересчитывает раскладку без перезапуска и потери данных.

Сверху показывать сессию и сводку состояния, снизу — доступные действия. Разделы: кошельки, подписи, переводы, Меркл,
блоки, эксперименты и журнал.

Использовать Tab/Shift+Tab, стрелки, Enter, Esc, F1, F2 и PgUp/PgDn. Горячие клавиши не перехватывают текстовый ввод.
Статусы сопровождаются словами, полные значения доступны в подробностях и экспорте. Поддержать `NO_COLOR`.

## 5. Проверки готовности и поставка

Для каждого этапа запускать тематические тесты через `--tests`, затем `gradlew.bat test`. Перед переходом к TUI весь
набор должен проходить, а оба headless-сценария — формировать полный комплект материалов.

Дополнительные проверки:

- Ошибка в последней транзакции не меняет подтверждённое состояние.
- Внешнее изменение исходной коллекции не меняет снимок.
- Несколько запусков не перезаписывают материалы друг друга.
- Недоступный каталог и ошибка записи корректно сообщаются.
- В экспорте отсутствуют закрытые ключи.
- Широкие таблицы, длинные HEX-значения и изменение размера окна не ломают фокус и ввод.
- В чёрно-белом режиме различимы выбор, ошибки и недоступные действия.

Финальная проверка:

1. `gradlew.bat test`.
2. `gradlew.bat nativeCompile`.
3. Запуск EXE с `--demo` и `--experiments` из отдельного каталога.
4. Проверка без доступного `java` в PATH и без `JAVA_HOME`.
5. Ручной прогон TUI в Windows Terminal с изменением размеров окна.
6. Проверка, что для распространения достаточно одного EXE; DLL извлекается автоматически, материалы создаются отдельно.
7. Подготовка README с запуском готового EXE, командами сборки для разработчика и описанием сохранённых материалов.

Полноценный отчёт DOCX/PDF, реальная сеть, майнинг, комиссии, восстановление сессии и импорт секретных ключей остаются
вне текущей задачи.

## 6. Правила коммитов

Все изменения проекта фиксировать в Git по Conventional Commits на текущей ветке. Новые ветки и worktree для
выполнения этого плана не создавать.

### Формат сообщения

Использовать формат `<type>(<scope>): <description>`. Область `scope` необязательна; описание должно кратко передавать
смысл изменения. Для несовместимого изменения контракта использовать `!` после типа или области и пояснение
`BREAKING CHANGE:` в теле сообщения.

Основные типы:

- `feat` — новая функциональность или реализация предметного поведения.
- `fix` — исправление ошибки.
- `test` — создание, наполнение и изменение тестов и тестовых данных.
- `refactor` — изменение структуры кода без изменения поведения.
- `build` — зависимости, плагины, настройки сборки и нативной упаковки.
- `docs` — план, инструкция и другая документация.
- `style` — форматирование без изменения поведения.
- `chore` — прочие служебные изменения проекта.

### Размер и момент фиксации

- Любое создание, изменение, удаление или переименование файлов проекта должно попасть в коммит. Фиксировать
  завершённые смысловые действия по ходу работы, не откладывая все изменения до конца этапа.
- Один коммит может объединять несколько связанных действий и файлов, если их описывает одна цель: например,
  создание набора файлов тестирования и общей тестовой инфраструктуры.
- Наполнение отдельных тестов и последующие изменения их сценариев можно фиксировать отдельными коммитами.
  Не требуется объединять все тесты подсистемы в один большой коммит или создавать коммит на каждое сохранение файла.
- Несвязанные изменения разделять. Тесты, реализацию и рефакторинг одной функции допускается фиксировать отдельными
  последовательными коммитами в соответствии с TDD.
- Перед коммитом проверять `git status`, diff и staged diff. Добавлять файлы явно по путям; не включать чужие
  несвязанные изменения. Сгенерированные файлы и результаты запусков, исключённые через `.gitignore`, не коммитить.
- Для изменений кода выполнять относящиеся к ним проверки, для изменений только документации — `git diff --check`.
  В конце этапа запускать весь набор тестов согласно разделу 3.
- После фиксации проверять результат коммита и отсутствие незакоммиченных изменений, сделанных в рамках текущего
  действия. Уже существующие несвязанные изменения пользователя оставлять нетронутыми.
- Не переписывать существующие коммиты через amend, rebase или reset и не отправлять изменения в удалённый репозиторий
  без отдельного указания пользователя.

### Коммиты в цикле TDD

Допускается отдельный коммит с новым падающим тестом на ещё не реализованное поведение. До коммита тест необходимо
запустить и убедиться, что причина падения ожидаемая. В теле сообщения указать проверенную команду и ожидаемое падение.
Такой промежуточный коммит не означает завершения задачи; следующая реализация должна перевести тест в успешное
состояние. Посторонние падения нельзя выдавать за ожидаемую фазу RED.

Пример последовательности:

1. `test(model): add test files and shared fixtures` — создать связанные файлы тестирования одним коммитом.
2. `test(model): cover invalid address format` — наполнить тест проверки адреса и зафиксировать ожидаемый RED.
3. `feat(model): validate address format` — реализовать поведение и получить GREEN.
4. `test(model): cover invalid public key length` — добавить следующий сценарий отдельным коммитом.
5. `test(model): refine invalid address cases` — изменить наполнение уже существующего теста.
6. `refactor(model): extract shared hex validation` — убрать дублирование при успешных тестах.

Изменения самого плана также фиксировать коммитами типа `docs`.
